# Derive a marketplace and pull base updates

Requirements: [openspec/specs/mb-base-update](../../openspec/specs/mb-base-update/spec.md) and [mb-layout](../../openspec/specs/mb-layout/spec.md).

## 1. Create your repo

Any of these works, because updates do not need shared git history:

- the GitHub **Use this template** button;
- `gh repo create acme-skills --template SashaMarchuk/marketplace-base`;
- `git clone https://github.com/SashaMarchuk/marketplace-base acme-skills`.

## 2. Initialise

```sh
./mb init --name acme-skills --display "Acme Skills" --owner "Acme" [--email ops@example.com] [--repo acme/acme-skills] [--examples all|none|<p,...>]
```

`init`:

- renders the seed files (README, USAGE, AGENTS, LICENSE, `marketplace.config.json`, `policy/org.json`, `.gitignore`, CODEOWNERS, `openspec/config.yaml`) for your name; LICENSE keeps the base copyright line and adds yours;
- deletes the examples you did not select;
- writes `.mb-lock.json` with the base tag, its commit and the hash of every base-owned file;
- runs `./mb gen` and `./mb check`, then prints next steps.

It refuses the name `marketplace-base` and refuses to run twice (an existing `.mb-lock.json`) unless you pass `--force`.

## 3. Who owns what

Every path has one owner class, defined in `.mb/ownership.json` (first match wins, in the order G, M, E, B, S; anything else is D):

| Class | Meaning | Examples | Base update |
|---|---|---|---|
| B | base-owned; do not edit | `tools/`, `docs/base/`, `mb`, `CONTRIBUTING.md`, `SECURITY.md`, `CLAUDE.md`, `openspec/specs/mb-*/`, `.github/workflows/mb-*.yml` | overwritten |
| E | base example plugins | `examples/plugins/` | overwritten, until you adopt them |
| S | seeds: rendered once by `init`, then yours | `README.md`, `USAGE.md`, `AGENTS.md`, `LICENSE`, `marketplace.config.json`, `policy/org.json` | never touched |
| D | yours | `plugins/<p>/`, `policy/teams/`, other workflows, other docs and specs | never touched |
| G | generated by `./mb gen` | manifests, marketplaces, `_mb/`, `docs/catalog.md`, `docs/base/rules.md`, marker blocks | regenerated |
| M | tool-managed | `.mb-lock.json` | rewritten |

Marker blocks such as `<!-- mb:catalog:begin -->` … `<!-- mb:catalog:end -->` inside your README, USAGE, AGENTS and `.gitignore` are generated; everything outside them is yours.

To change base behaviour, open a PR against the base instead of editing B files. `./mb check` (CHK-16) reports any edited B or E file.

## 4. Update from the base

```sh
./mb base-update [--to vX.Y.Z] [--dry-run]
```

0. Stops (exit 2) if the working tree is not clean or the target tag is older than the locked tag.
1. Picks the newest stable tag of `base.url` (pre-release tags such as `v1.3.0-rc.1` are never picked unless you pass `--to`).
2. Stops (exit 6) if you edited or added files under the base tooling (`tools/`, `.mb/ownership.json`, `.mb/base-version.json`, `.mb/migrations/`, `mb`, `mb.cmd`), unless `--force`.
3. Fetches the tag, checks out the new tooling, and re-runs itself with it.
4. Applies each file decision: unchanged base files are updated; files the base removed are deleted; files the base re-classified as yours are released (left in place); your D and S files are never touched.
5. Runs any migrations for the versions crossed and reports the S files they edited.
6. Writes the new lock, runs `./mb gen` and `./mb check --fast`, and prints a report.

`--dry-run` prints the plan and writes nothing.

### Conflicts

A conflict is a base-owned file you edited, or a file of yours at a path the new base adds. By default it is left untouched and the update exits 6.

| Option | Effect |
|---|---|
| (none) | report and leave conflicts untouched; exit 6 |
| `--force` | overwrite conflicts with the base version (your edits are lost) |
| `--keep` | keep your version; its old lock hash is kept, so `./mb check` stays red (the update exits 1) and the next update reports it again until you resolve it |
| `--continue` | resume an interrupted update (uses the stored commit) |
| `--no-workflows` | leave `.github/workflows/mb-*.yml` untouched (used by the scheduled update without a token) |

### Scheduled updates

Set the repository variable `MB_BASE_UPDATE` to `true` to run `mb-base-update.yml` weekly. It runs the update in a read-only job and publishes the result as branch `mb/base-update-<tag>`:

- with a `MB_UPDATE_TOKEN` secret (PAT or GitHub App token with `contents`, `pull-requests` and `workflows` write), it opens the PR;
- without it, it pushes the branch, skips workflow files, and writes a compare link and checklist to the job summary. Open the PR yourself, then run `./mb base-update` locally to update the workflow files. (Events made with the default `GITHUB_TOKEN` do not start PR checks, so the workflow never opens the PR with it.)

## 5. Adopt an example

```sh
./mb adopt code-review
```

Moves `examples/plugins/code-review` to `plugins/code-review`, where it is yours (D): base updates no longer touch it and you can bump and edit it.

## 6. Migrations

A base release that renames or moves something you own ships `.mb/migrations/<x.y.z>.mjs`. `base-update` runs it once (it is idempotent) and lists the S files it edited, and [CHANGELOG.md](CHANGELOG.md) has a "Migration" note for it. Within one major version, base changes to S file schemas are additive only.
